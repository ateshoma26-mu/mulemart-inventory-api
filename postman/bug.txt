1. Missing item returns null instead of 404

GET /inventory/{itemId} and GET /inventory/{itemId}/summary: if the id is not in MySQL, the Transform sets payload to null and you get 200 with an empty/null body.

PUT already does it right: isEmpty(payload) → raise APP:NOT_FOUND → 404. GET should do the same after the SELECT (and not cache that miss).

2. Cache store failure turns a good GET into 500

GET /inventory/{itemId}: DB + Transform succeed (your SKU-DEMO-001 JSON), then os:store throws → 500 with that JSON still in the body.

PUT already wraps cache remove in Try / On Error Continue (OS:KEY_NOT_FOUND). GET should wrap cache store the same way: if Object Store fails, still return 200 with the item. Reading inventory should not fail only because cache write failed.

Object Store requires a key. null → MULE:UNKNOWN → Postman 500. The Transform already built the JSON, so you still see SKU-DEMO-001 in the body.

Why itemId is null there

At the start of GET, attributes.uriParams.itemId is SKU-DEMO-001 (that is how os:contains and the SELECT work).

After DB Select and Transform, Mule replaces the message. HTTP attributes (including uri params) are often gone. PUT avoids this by copying the id first:

vars.itemId = attributes.uriParams.itemId

GET never does that. It still uses attributes.uriParams.itemId on Store In Cache, which is now null.

Fix

First box on GET-by-id: Set Variable itemId from attributes.uriParams.itemId (same as PUT).
Use vars.itemId for contains / retrieve / SELECT / store.
Optional: wrap Store In Cache in Try / On Error Continue so a cache write never fails the GET.
That is the same 500 you saw earlier with a good body. The console line just names the cause.
